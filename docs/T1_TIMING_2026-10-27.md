## Approved buffer / monitoring A/B completed

All four conditions passed internal event accounting: 834, 833, 835 and 835
matched input/output Note Ons respectively (3,337 total, no extra/missing Ons).
Six approximately four-second wire/native/legacy passes ran in each condition.
The same source, test lane and receive-only sink were retained.

| Audio buffer | Original monitoring-option state | After toggling Reduced Latency When Monitoring |
| --- | ---: | ---: |
| 64 samples | ~9.08 ms | ~3.48 ms |
| 128 samples | ~14.43 ms | ~6.16 ms |

Table values summarize the two native pass medians; wire medians were within
about 0.01 ms. Legacy JS continued to add delay and larger tail jitter.
Raw per-pass summaries are in `T1_BUFFER64_ORIGINAL_2026-10-27.json`,
`T1_BUFFER64_TOGGLED_2026-10-27.json`,
`T1_BUFFER128_TOGGLED_2026-10-27.json` and
`T1_BUFFER128_ORIGINAL_2026-10-27.json`.

The menu accessibility interface did not expose its original checkmark; the
evidence deliberately names states original/toggled, not a directly observed
On/Off value. The lower-delay state is consistent with enabling this option:
[Ableton's documentation](https://www.ableton.com/en/manual/working-with-instruments-and-effects/#device-delay-compensation)
explains that enabling it removes compensation waits on input-monitored tracks,
but those tracks can then be out of sync with compensated tracks/returns.

Recommendation for the next audible/hardware trial: native quantizer, Follow
Gate, separation zero, 64 samples if stable, Reduced Latency When Monitoring
enabled. Then measure FH-2 pitch/gate/audio alignment; do not assume that a low
software MIDI delay guarantees alignment with direct hardware triggers.

Restoration completed: monitoring option toggled exactly twice (back to its
original state); buffer visually verified at 64 samples / 48 kHz; temporary
sink Track output explicitly Off, Sync/Remote unchanged Off; test track No
Output; all four fixtures bypassed; temporary capture process stopped and its
endpoint removed. Buffer changes paused the clocked T-1 stream; a brief Live

Hardware routes and MIDI settings were not changed. No new release was published.

## Completed Live software-output comparison

After the source was restarted, six live passes completed with **2,024 matched
Note Ons**, no extra/missing Ons, and correct Off counts after explicit phase-
boundary orphan accounting. Both native passes discarded one initial orphan
Off after Panic, as designed. Internal fixture validation passed.

The separate CoreMIDI listener measured T-1 ingress timestamps to Live's
receive-only software destination. Discarding 300 ms at each phase edge yielded:

| Path | Samples, pass 1 / 2 | Median ms, pass 1 / 2 | p95 ms, pass 1 / 2 | Worst ms |
| --- | ---: | ---: | ---: | ---: |
| Wire | 318 / 318 | 9.083 / 9.081 | 9.131 / 9.136 | 19.210 |
| Native | 317 / 318 | 9.084 / 9.088 | 9.125 / 9.157 | 16.178 |
| Legacy JS | 318 / 318 | 10.135 / 10.164 | 16.435 / 18.387 | 28.158 |

These use max(output timestamp, callback arrival) minus input packet timestamp;
callback and scheduled metrics are also retained in the JSON. The buffer was
rechecked: **64 samples, 48 kHz**, reported audio input 2.06 ms / output 2.15 ms.
No buffer or compensation options were changed for this comparison.

Conclusion: native processing contributes essentially no measurable median
delay above the same fixture's wire path. There is a roughly **9.1 ms baseline**
in this current Live/software-MIDI topology even without quantization. The old
JS path adds approximately 1.1 ms median and substantially more tail jitter.
The baseline's precise cause is not yet isolated; it must not all be attributed
to the quantizer, the buffer, or FH-2. FH-2 was not in the measurement.

The repeated source is pitch 55 / velocity 127 at about 30 ms spacing. FIFO
matching relies on the internally verified one-On-per-input sequence; identical
repeated messages have no transmitted unique instance ID. This is not an
arbitrary-loss/reorder proof. The capture parser ignores non-channel-1 notes.
One unmatched output at the initial capture cut and the final in-flight note
are boundary events, excluded from phase statistics.

Evidence: `T1_NATIVE_INTERNAL_2026-10-27.json` and
`T1_LIVE_LOOPBACK_2026-10-27.json`. No claim is made about upstream USB travel,
FH-2 CV conversion, oscillator/gate alignment, or audio round-trip latency.

Next controlled comparison: Reduced Latency When Monitoring and buffer 64/128,
with explicit permission requested and original settings restored afterward.

Cleanup after this completed run: the capture reached its timeout and removed
its virtual endpoint (confirmed absent in Live MIDI settings). The completed
fixture was bypassed and its track explicitly restored to No Output. No hardware
route or buffer/compensation setting was changed.

No extra or unmatched Note Ons occurred. Initial aggregate lifecycle validation
flagged one fewer native Note Off per pass. Native consumes orphan Note Offs
after phase reset, unlike raw wire/legacy passthrough. The fixture now explicitly
counts initial boundary orphan Offs, but the corrected real-input repeat still
needs to run: the source stopped, producing zero samples, correctly rejected.
Thus this preliminary result is timing evidence, **not a completed lifecycle
acceptance test**. Separate native lifecycle acceptance tests already exist.

A separate 15-second CoreMIDI input capture found channel 1 sent 496 Ons and
496 Offs, all pitch 55, with median inter-On spacing 30.231 ms (range
28.876–33.780 ms). Other T-1 channels were transmitting too, but Live's test
lane selected only channel 1. This source is useful for repeated-note timing,
not a varying-pitch musical regression test.

## Next measurement

`tools/capture_t1_loopback.swift` creates a temporary **receive-only** software
destination, Codex Latency Sink, and captures T-1 plus Live output timestamps.
It creates no MIDI output port and cannot send to hardware. Live must have
Track output enabled for this temporary destination. Permission was requested;
the first attempt left settings unchanged and no hardware output route was selected.

After explicit approval, a second attempt enabled only the sink's Track output
(Sync/Remote remained off) and routed the disposable test lane to it. The sink
received Live initialization traffic, but **no T-1 notes arrived**. The external
input measurement therefore remains blocked, not zero-latency or passed.
The fixture is bypassed, test lane restored to No Output, and sink Track output
restored to Off. Hardware settings were not changed.

`python3 tools/build_native_timing.py --live --loopback` builds the corresponding
test AMXD. Route it only to the diagnostic sink, never FH-2/synth hardware.
The non-loopback `--live` fixture has no MIDI output. Use the same buffer,
monitoring and compensation settings across all passes. Restore No Output and
disable the temporary port after the run.

`tools/analyze_t1_loopback.py` matches repeated pitches FIFO and reports both
CoreMIDI callback arrival and scheduled output timestamps. Its three accounting
tests pass; these tests do not establish real-world latency. The live fixture
waits for incoming notes before starting its comparison, and empty measurements
are explicitly invalid.

Still unmeasured: full T-1 USB ingress → Live output latency, FH-2 conversion,
CV/gate alignment, and audible timing under the user's performance setup.
Hold/Settle and ensemble separation deliberately introduce their configured
waits; native Follow Gate plus separation zero adds no intentional timer wait.
